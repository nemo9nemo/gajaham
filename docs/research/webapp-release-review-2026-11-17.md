## 1. 판단 요약

분석 기준 커밋의 가자함은 **로그인하면 여러 지원 브라우저에서 개인 기록을 다시 조회하는 장소 링크·메모 보관함**까지 구현했다. 게스트 저장, 명시적 계정 이동, 중복 방지, 편집 충돌 방지, 휴지통·탈퇴의 기반은 갖췄다. 최초 분석 시인 2026-11-17의 재실행에서 로컬 자동 검사 28개가 통과했다. 이후 문서 보완에서 이를 재실행한 것은 아니다.

다만 **일반 사용자에게 공개 출시할 준비가 완료됐다고 판단할 수는 없다.** 위 운영 증거에는 실제 Worker/D1·App Check·관리 자격증명·공개 운영정보·실메일·Galaxy·공개 배포가 미완료로 남아 있다. 최초 분석과 문서 보완에서 운영 콘솔에 접속하지 않았으므로 11월13일 이후 외부 설정이 바뀌었는지는 확인하지 않았다.

출시 작업은 다음 두 목표로 구분하는 것이 적절하다. 이는 작업 순서 제안이며 기존 제품 범위를 변경하는 결정은 아니다.

| 목표 | 제공할 가치 | 필요한 조건 |
|---|---|---|
| 개인 보관함 베타 | 링크·장소·메모를 보관하고 같은 계정으로 다시 찾기 | 3절의 출시 조건 통과, 현재 제공 범위를 명확히 소개, 4절의 주요 사용 흐름 보완 |
| 원래 구상의 가자함 | 장소를 지도에서 보고 두 사람이 선택 공유하고 DM으로 수집 | 베타 기반에 지도·연결·공유 사본·수신 경로·권한 검증을 단계적으로 추가 |

**가장 먼저 할 일은 운영 연결과 검증을 끝내는 것이다.** 동시에 계정 이동의 한도 대응·편집 입력 보호·모바일 사용성을 개선한다. 지도·공유·DM을 한 번에 붙이면 비용과 권한 문제의 원인을 구분하기 어려워진다.

## 2. 분석 범위와 현재 구현

### 2.1 상태 표기의 의미

- **분석 기준 확인**: 위 기준 커밋의 코드를 읽거나 2026-11-17 최초 분석에서 실제 재검사한 내용. 후속 문서 갱신 때마다 재검사했다는 뜻은 아니다.
- **기존 증거**: 저장소에 남은 과거 검사/설정 기록. 실행일과 대상을 함께 읽으며 운영 재검사를 뜻하지 않는다.
- **미검증**: 운영 환경 또는 실기기의 실행 증거가 없는 내용.
- **개선 제안**: 아직 구현·승인되지 않은 설계 방향. 성능/사용성 효과는 적용 후 확인해야 한다.

### 2.2 구성과 책임

| 영역 | 현재 역할 | 출시 분석에서의 해석 |
|---|---|---|
| `app-web/` | Vite·Firebase Auth Web, 게스트 IndexedDB, 계정 API 호출, 실제 UI | 이번 웹앱의 주 대상 |
| `worker/` | Workers API, D1 저장, JWT/App Check, 최신 계정 상태, 삭제/Cron | 실제 배포/무료 한도 검증이 필요한 서버 |
| `functions/src/domain.mjs` | 입력/URL 정규화·한도·공통 순수 함수 | 현재 웹/Worker에서도 사용. 폴더명만 보고 폐기하면 안 됨 |
| `functions/`의 나머지 서버 | 이전 Functions/Firestore 구현 | 현 배포 대상과 분리 |
| `web/` | 58개 화면 정적 목업 | 후속 UX 참고 자료. 실제 지도/공유 구현 증거가 아님 |
| `android/`, `account/` | 과거 Android·인증 삭제 자산 | 현 웹 서버 동기화·탈퇴 완료 증거로 대체할 수 없음 |

현재 데이터 흐름은 다음과 같다.

```text
게스트 → 이 브라우저의 IndexedDB
           └─ 사용자가 계정에 담기를 확인 → 서버 확인된 기록만 로컬에서 정리

로그인 → Firebase Auth + App Check → Worker → UID별 D1 개인 원본
                                          └─ 삭제 pending → 후속 작업/5분 Cron
```

계정 기록은 화면 메모리에 두며 영속 오프라인 큐를 제공하지 않는다. 로그인만으로 게스트 기록을 올리지 않고, 다른 사용자의 개인 기록을 조회하지 않는다. 이 경계는 개선 후에도 유지해야 한다.

## 4. 분석 항목과 사용 흐름 보완 현황

**P1은 개인 보관함 베타 전 우선 보완**, **P2는 베타 사용 결과를 보며 진행할 기능/구조 개선**이다. 아래 코드 근거는 함수/선택자 기준이며 줄 번호 변화에 영향을 덜 받도록 적었다. 규모·장애에 관한 항목은 별도 표기가 없으면 코드 분석에 따른 위험이며 실제 운영 장애 재현 결과가 아니다.

아래 '근거/문제'는 최초 분석 시 `f714893`의 상태를 보존한 것이다. WEB-06의 수정 결과는 각 항목의 '진행'과 검증 증거를 따른다. 남은 운영/실기기 검사를 로컬 구현 완료와 합치지 않는다.

### U01. 게스트 기록을 계정에 옮기는 작업의 중단·한도 대응 — P1

- **진행:** WEB-06 구현·로컬 검증 통과. 150건의 중단/재개·중복 유지·원인별 429, 연속 503 뒤 재접속, 계정 변경을 확인했다. 요청 ID/서버 확인 후 로컬 정리 경계를 유지한다.

- **근거/문제:** `main.mjs`의 `confirm-transfer`는 휴지통 외 기록을 한 번에 순회하며 건별 create를 호출한다. 실패 이유와 관계없이 다음 항목을 계속 시도한다. `service.mjs`의 `rateLimit`는 UID당 분당 120회이며 조회도 포함된다. 대량 이동이 충분히 빠르면 한도에 걸릴 수 있고, 429/503이 이어져도 불필요한 호출과 긴 전체 화면 잠금이 계속된다. 현재 안전장치 덕분에 실패 원본은 남지만 실패 원인을 구분하기 어렵다.
- **수정 방향:** 10~20건 등 작은 작업 묶음으로 진행하고 성공/중복/한도/통신 실패를 나눈다. 현재 서버는 호출 제한·보관 건수/용량·누적 생성요청 한도를 모두 429로 반환하므로, U06에서 제안한 고정 오류 이유로 재개 조건을 구분한다. 호출 제한은 대기 후 사용자가 남은 항목만 재개하고, 보관 건수/용량은 정리·입력 축소를, 누적 생성요청 한도는 문의를 안내한다. 연속 503은 일시 중단하고 연결 회복 뒤 사용자가 재개하게 한다. U01과 U06의 오류 계약을 함께 설계하며 별도 선행 작업으로 강제하지 않는다. 중단은 진행 중 한 건의 결과를 확인한 뒤 수행한다. 기존 requestId와 서버 확인 후 로컬 정리 규칙을 유지한다. 항목 선택·전체 선택은 후속으로 붙일 수 있다.
- **수정 대상:** [계정 이동 UI](../../app-web/src/main.mjs), [요청/오류 처리](../../app-web/src/gateway.mjs), [서버 한도](../../worker/src/service.mjs), [게스트 이동 식별자](../../app-web/src/guest.mjs).
- **완료 기준:** 합성 기록 150건, 중간 429/503, 중단/재접속, 중간 계정 전환을 검사한다. 429는 호출·보관 건수/용량·누적 생성요청 한도를 각각 확인하고, 대기로 해소되지 않는 한도에 대기 후 재개를 안내하지 않는다. 중단 이후 요청 폭주가 없고 성공 건만 정리되며 같은 요청 재시도로 중복/삭제 기록 부활이 없어야 한다. 계정 기록의 영속 오프라인 큐는 만들지 않는다.

### U02. 중복 저장 시 기존 기록을 바로 찾게 하기 — P1

- **진행:** WEB-06 구현·로컬 검증 통과. 기존 대상/휴지통을 명시적으로 열고, 메모 비교 후 사용자가 선택·저장한다. 그사이 삭제된 대상은 재조회해 부재를 안내하며 자동 재생성하지 않는다.

- **근거/문제:** 서버 create는 중복이면 기존 `id`를 돌려주지만 `submitRecord`는 안내 후 목록만 다시 읽는다. 중복이 휴지통에 있거나 기록이 많으면 사용자가 직접 찾아야 한다.
- **수정 방향:** 중복 결과에 `기존 기록 보기`를 제공한다. 기존 상태가 휴지통이면 복원 가능 여부를 보여주고 명시적으로 복원하게 한다. 새로 입력한 메모를 자동 덮어쓰지 말고 메모 차이를 확인해 반영하도록 한다.
- **수정 대상:** [submitRecord·recordDialog](../../app-web/src/main.mjs), [create의 중복 반환](../../worker/src/service.mjs).
- **완료 기준:** 일반 기록/휴지통/조회 중 영구 삭제된 대상의 중복을 각각 검사한다. 정확한 기존 기록으로 이동하며 무단 복원·필드 덮어쓰기가 없어야 한다.

### U03. 충돌·창 닫기에서 편집 중 내용을 보호하기 — P1

- **진행:** WEB-06 구현·로컬 검증 통과. dirty 닫기 취소·페이지 이탈 경고 연결·최신 값 비교와 선택 필드 재저장·계정 변경 후 초안 제거를 확인했다. 초안/비교값은 UID/세션 메모리뿐이다.

- **근거/문제:** revision 충돌은 올바르게 거절하지만 안내는 창을 닫고 최신 기록을 읽으라고 한다. `closeDialog`는 폼을 제거하므로 그 과정에서 사용자의 편집 내용이 사라진다. 수정 여부를 검사하는 닫기 경고도 없다. 이는 서버 데이터 유실 결함과는 구분되는 입력 경험 문제다.
- **수정 방향:** 폼 dirty 상태를 추적해 닫기 전에 확인한다. 충돌 시 현재 입력과 최신 서버 값을 같은 화면에서 비교하고, 사용자가 선택한 필드만 최신 revision 기준으로 새 저장 요청을 보내게 한다. 초안은 해당 UID/세션의 메모리에서만 보관하고 로그아웃·계정 변경 때 제거한다. 비밀번호는 보관하지 않는다.
- **수정 대상:** [openDialog·closeDialog·submitRecord](../../app-web/src/main.mjs), [aborted 안내](../../app-web/src/gateway.mjs).
- **완료 기준:** 두 브라우저가 같은 기록을 수정해도 오래된 값이 자동 덮어쓰지 않는다. 최신 값 확인 과정에서 현재 입력을 유지하고, 계정 전환 시 이전 초안은 노출되지 않는다.

### U04. 모바일 가독성·터치·대화상자 접근성 — P1

- **진행:** WEB-06에서 모바일 한 열·주요 터치 44px·보조 글자 확대·dialog 이름/오류/포커스·스크롤 액션을 구현했다. 360/390/412px·가로/짧은 높이·큰 폼 글자 합성 검사가 통과했고 화면을 시각 확인했다. 실제 Galaxy/TalkBack·모바일 키보드/뒤로가기는 L06에서 확인한다.

- **근거/문제:** 390px 화면에서도 두 열 카드이고 주소·상태·날짜에 8~10px 글자가 많다. `.icon-button`은 32px이며 필터 등 주요 버튼의 터치 여유가 작다. `openDialog`는 제목을 넣지만 dialog에 `aria-labelledby`를 연결하지 않는다. 스크린리더 이름·실제 터치 오류·키보드 겹침은 이번에 측정하지 않았다.
- **수정 방향:** 휴대전화 기본을 한 열로 검토하고 보조 텍스트도 읽을 수 있게 확대한다. 주요 터치 영역은 44px 이상을 프로젝트 설계 목표로 삼는다. 제목 ID/`aria-labelledby`, 오류 필드 연결, 적절한 초기 포커스와 닫은 뒤 포커스 복귀를 넣는다. 키보드가 열린 작은 높이에서 하단 액션에 접근할 수 있게 한다.
- **수정 대상:** [모바일 CSS](../../app-web/src/style.css), [대화상자/모바일 메뉴](../../app-web/src/main.mjs).
- **완료 기준:** 360/390/412px, 가로 화면·큰 글자·키보드 상태를 확인한다. 가로 넘침·버튼 가림 없이 주요 작업이 가능하고 TalkBack으로 대화상자 제목/오류를 구분할 수 있어야 한다. 44px 목표는 여기서 법적 준수 판정을 뜻하지 않는다.

### U05. 조회·정렬·검색의 규모 대응 — P1(측정/표시), P2(서버 확장)

- **진행:** WEB-06에서 최근 수정순으로 표시하고 전체 조회/검색/건수는 유지한 채 카드 DOM을 50개부터 늘린다. 실제 로컬 D1 201건 커서와 0/200/201/2500건 클라이언트 측정을 확인했다(8.1절). 운영 CPU·API/DB 전체 비용 측정과 서버 정렬/필터·점진 조회는 남아 있다.

- **근거/문제:** `refresh`가 200건 페이지를 최대 26회 순차 조회한 뒤 전체를 렌더링한다. 포커스 복귀 후 15초가 지났으면 전체 조회가 가능하다. `visibleRecords`는 매 입력마다 필터/정렬하고 `renderCards`는 카드 전체를 다시 만든다. 또한 화면은 `최근 담은 순`인데 정렬 키는 `updatedAt`이므로 편집한 오래된 장소가 앞에 나온다.
- **수정 방향:** 먼저 표시를 `최근 수정순`으로 맞추거나 실제 `createdAt` 정렬을 선택하게 한다. 허용 용량 내 합성 데이터로 첫 표시 시간·DOM 수·API/DB 사용량을 측정한다. 이후 첫 페이지부터 보여주고 `더 보기`/점진 렌더링을 도입한다. 서버 정렬·필터는 UID 범위와 안정적인 `(시각, ID)` 커서/인덱스를 설계한 뒤 추가한다. 일부만 읽은 상태에서는 전체 검색/건수인 것처럼 표시하지 않는다.
- **수정 대상:** [refresh·visibleRecords·renderCards](../../app-web/src/main.mjs), [list](../../worker/src/service.mjs), [query 어댑터](../../worker/src/store.mjs), [스키마](../../worker/migrations/0001_documents.sql).
- **완료 기준:** 0/200/201건과 2MiB 한도 내 큰 데이터에서 누락·중복·잘못된 전체 건수가 없어야 한다. 오래된 페이지 응답이 새 저장을 덮지 않는 기존 회귀도 유지한다. 이미 적용된 migration은 수정하지 않고 새 migration을 추가한다.

### U06. 오류 안내와 메일 재발송 경험 — P1

- **진행:** WEB-06에서 고정 오류 이유/호출 제한 재시도 시각, U01과 같은 조치 안내, 한국어 메일·60초 재발송 대기·가입 여부 동일 안내와 설정 오류 전파를 구현·로컬 검증했다. 실제 메일 도착/링크 왕복은 L05 미실행이다.

- **근거/문제:** `errorMessage`가 `resource-exhausted`를 모두 같은 문구로 처리해 잠깐 기다릴 호출 제한과 휴지통 정리가 필요한 저장 한도를 구분하기 어렵다. `resetPassword`는 네트워크/호출 제한 외 오류를 삼키므로 설정 문제도 정상 접수처럼 보일 수 있다. 확인 메일 재발송에는 사용자 대기시간 표시가 없고 Auth 언어 설정도 코드에 없다.
- **수정 방향:** 서버에 개인정보 없는 고정 오류 이유(`rate-limited`, `record-limit`, `storage-limit`, `operation-limit` 등 제안값)와 필요 시 재시도 시각을 정한다. U01의 계정 이동에서도 같은 오류 이유를 사용한다. UI는 호출 제한에 대기/재시도, 보관 한도에 휴지통 정리·입력 축소, 누적 생성요청 한도에 문의를 연결한다. 재설정은 존재하지 않는 계정도 같은 문구로 보호하되 설정/서비스 오류를 무조건 성공 처리하지 않는다. 메일 언어를 한국어로 지정하고 재발송 대기시간을 보여준다.
- **수정 대상:** [gateway](../../app-web/src/gateway.mjs), [메일/오류 UI](../../app-web/src/main.mjs), [서버 오류 이유](../../worker/src/service.mjs).
- **완료 기준:** 미가입/가입 이메일에서 존재 여부가 드러나지 않는다. 호출 제한·저장 한도·서비스 불가의 조치가 구분되고, 재발송 연속 클릭이 불필요한 메일 요청을 만들지 않는다.

### U07. 저장 위치·게스트 손실 위험을 행동 직전에 알리기 — P1

- **진행:** WEB-06에서 게스트 저장 범위/손실 가능성·로그인 후 별도 계정 이동을 안내하고, 로그인/서버 연결 상태를 분리했다. 계정 최초 조회 실패와 합성 IndexedDB 용량 오류에서 완료 오표시가 없음을 확인했다. 시크릿/인앱 브라우저 실기기 지원 검증은 미실행이다.

- **근거/문제:** 브라우저 저장 안내와 개인정보 페이지는 이미 있다. 그러나 게스트 생성 성공 문구는 `이 브라우저에 담았어요`이며, 인스타그램 내부 브라우저/시크릿/사이트 데이터 삭제 후 기록이 사라질 수 있다는 안내가 핵심 저장 행동에서는 약하다. 계정 초기 목록 실패 시에도 상단은 `계정에 보관 중`으로 표시된다.
- **수정 방향:** 첫 게스트 저장 후 짧게 저장 범위·로그인 후 별도 이동 필요를 안내하고 원하면 계정 이동으로 연결한다. 로그인 상태와 서버 조회/저장 상태를 분리해 `로그인됨·연결 확인 필요` 등을 표시한다. 브라우저 저장 불가/용량 오류는 저장 성공으로 보이지 않게 한다. 사이트 주소를 임의로 바꾸어 게스트 기록이 분산되지 않게 정식 origin을 유지한다.
- **수정 대상:** [renderApp·submitRecord](../../app-web/src/main.mjs), [IndexedDB 처리](../../app-web/src/guest.mjs).
- **완료 기준:** 로그인만으로 자동 업로드되지 않는다. 저장 실패는 명확하고 첫 사용자가 기록의 저장 위치와 다른 기기 조회 조건을 설명할 수 있어야 한다. 시크릿/인앱 브라우저 제한은 실제 확인한 환경만 지원표에 기록한다.

### U08. 만료 휴지통의 물리 삭제와 운영 상태 확인 — P1(절차), P2(자동화)

- **진행:** WEB-06에서 만료 기록 수·가장 오래된 삭제 시각의 집계와 지연 문의 절차를 추가하고 로컬 D1에서 확인했다. 실제 운영 담당/주기/목표시간은 L08, 모든 비활성 계정의 정기 정리는 P2 후속이다. 현재 삭제/Cron 동작은 바꾸지 않았다.

- **근거/문제:** `list`는 만료 기록을 모두 숨기지만 페이지당 최대 3건만 물리 정리한다. `scheduled`는 계정 탈퇴와 `purge_at` 메타를 정리하며, 모든 비활성 계정의 만료 휴지통을 정기 삭제하는 구조는 아니다. 현재 안내도 접속 시 순차 정리라고 명시한다. 30일 경과 즉시 모든 원문이 사라진다고 약속하면 실제 동작과 어긋난다.
- **수정 방향:** 우선 현재 안내/문의 대응에서 복원 불가 시점·현재 DB 삭제·복구 이력 소멸을 구분한다. 삭제 지연/만료 건수 집계를 운영에 넣는다. 정기 정리가 필요하면 원본에 단순 TTL 삭제를 걸지 말고, 출처 인덱스·계정 count/bytes·삭제 재생성 차단 ID를 함께 처리하는 제한된 작업을 설계한다. 탈퇴 작업에 우선권을 준다.
- **수정 대상:** [list·mutate·finishDeletion](../../worker/src/service.mjs), [scheduled](../../worker/src/api.mjs), [health.sql](../../worker/operations/health.sql), [개인정보 안내](../../app-web/src/privacy-content.mjs).
- **완료 기준:** 장기 미접속·대량 만료·중간 실패에서도 원문/출처/집계가 일치한다. 만료/영구 삭제된 기록이 오래된 create 재시도로 되살아나지 않는다. 정리 목표시간은 정책 확정과 운영 측정 후 정한다.

## 6. 구조·검증·운영 문서에서 손볼 내용

## 7. 권장 작업 순서와 통과 기준

정확한 일정은 운영 접근·외부 승인·기기 검증에 좌우되므로 근거 없는 출시일을 정하지 않는다. 아래 순서대로 작업 브리프를 만들면 된다.

| 단계 / 작업 묶음 제안 | 작업 내용 | 다음 단계로 넘어갈 증거 |

### 7.2 베타에서 확인할 제품 지표 제안

초기에는 동의한 소규모 사용자의 관찰과 집계만으로 시작할 수 있다. 외부 분석 SDK 도입을 전제로 하지 않는다.

- 링크를 받은 뒤 첫 기록을 저장하기까지 걸린 시간과 포기한 단계.
- 저장한 장소를 나중에 검색해 원본/외부 지도로 다시 여는 데 걸린 시간.
- 게스트→계정 이동의 성공/중복/실패 건수와 사용자가 이유를 이해하는지 여부.
- 개인 베타의 재방문, 공유 기능 이후 두 사람 모두 저장·조회·장소 선택을 하는지 여부.
- 저장 1건/목록 조회/탈퇴당 DB 행 읽기·쓰기·CPU와 하루 사용량. 계정별 허용량만 보고 운영 가능 인원을 추정하지 않는다.

이 지표는 제안이며 아직 계측·달성한 결과가 아니다. 장소 원문·검색어·메일·UID를 분석 로그에 추가하지 않는다.

지도/공유/DM은 [제품 기획](../personal-shared-map-plan-2026-10-12.md)의 선택 공유·맵별 독립 사본·연결 해제 규칙을 먼저 계약/검증 시나리오로 내린 뒤 구현한다. 이 보고서가 작성됐다는 사실과 출시 또는 제안 기능의 구현 완료는 구분한다.
