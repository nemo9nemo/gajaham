# 웹 로그인 계정의 서버 원본·여러 기기 조회 계약

기준: 2026-11-03 [결정0008](../decisions/0008-account-cloud-records.md)·[구현 결정0009](../decisions/0009-web-personal-api.md). WEB-01의 개인 저장·인증·기기 간 재조회는 코드/공식 Emulator·독립 브라우저에서 검증한다. 운영 프로젝트·실메일·Galaxy·공개 배포는 미실행이다. [게스트 계약](web-local-data.md), [인증·공유 계약](auth-and-guest.md)을 함께 따른다.

## 사용자에게 제공할 동작

“로그인한 기록은 계정에 저장됩니다. 다른 기기나 브라우저에서도 같은 계정으로 로그인해 볼 수 있습니다. 로그인하지 않고 저장한 기록은 이 브라우저에만 남습니다.”

기본은 URL 접속이며 설치를 요구하지 않는다. ‘어디서든’은 네트워크가 가능한 지원 브라우저에서 같은 유효 계정으로 접근하는 범위다. 미전송 입력·영구 삭제된 원본·정지/탈퇴 계정까지 복구를 약속하지 않는다.

## 원본과 식별

| 데이터 | 원본/식별 | 공유/삭제 경계 |
|---|---|---|
| 게스트 기록 | 현재 브라우저/프로필/origin의 IndexedDB guest 영역 | 서버 계정 생성 없음. 사용자 선택 전 업로드하지 않음 |
| 계정 개인 기록 | 서버의 검증된 UID 영역 + 개인 기록 ID | 저장한 장소·출처 링크·직접 입력·메모/메뉴·방문·분류·처리함·휴지통 등을 계정에 보관. 상대에게 자동 공개하지 않음 |
| 계정 캐시/구독 | 현재 인증 UID와 세대에 묶인 클라이언트 상태 | 서버 원본의 대체가 아님. 계정 전환/로그아웃 때 닫고 제거 |
| 미저장 입력 | 현재 폼/요청 상태 | 서버 확인 전 계정 기록으로 표시하지 않음. 실패 때 입력 보존/재시도 안내, 다른 기기 조회 보장 없음 |
| 공유 사본 | 공유 맵 ID·현재 참여권·별도 기록 ID | 사용자가 선택한 필드만 별도 복제. 개인 원본과 이후 편집/삭제를 자동 연결하지 않음 |

UID는 SDK/서버에서 검증한다. 같은 이메일의 신규 가입/UID 변경으로 이전 기록을 자동 연결하지 않는다. 문서 경로·인덱스·기존 중복 키 규칙은 WEB-01에서 고정한다. 개인·공유의 비용은 합산하되 인가/사본 수명은 분리한다.

WEB-01은 `users/{검증UID}/records/{UUID}` 원본과 같은 UID의 `sources/{canonicalURL의SHA256}` 중복 인덱스를 사용한다. 직접 클라이언트 DB 접근은 모두 거절한다. 서버 callable API만 Auth 최신 토큰/회수·상태와 입력을 검증한 뒤 Admin 기본 자격증명으로 처리한다. 계정당5000건·직렬화한 기록 UTF-8 2MiB이며 DB 인덱스/메타/실제 과금 용량의 상한은 아니다. 페이지200개·분당120개 API 요청을 제한한다. 정상 저장 응답을 메모리에 적용하고 전체 재조회는 재진입/명시적 갱신에 수행한다. 조회 세대가 늦은 결과를 차단한다.

## 서버 인가와 변경

- 개인 목록·읽기·추가·수정·휴지통·복원·영구 삭제 모두 요청 UID와 소유자를 검사한다. 소유자 변조·게스트/다른 UID/만료 인증의 직접 API 요청도 거절한다. 공유는 이메일 확인·현재 참여권·계정 상태를 별도로 검사한다.
- Firebase Auth + Firestore Standard를 우선 구현 방향으로 하며 Rules/API가 실제 인가를 담당한다. 관리자 키를 클라이언트에 넣지 않고 관리자 API에도 별도 인가를 둔다. 프론트의 목록 필터/로그인 플래그로 대체하지 않는다. [공식 규칙](https://firebase.google.com/docs/firestore/security/rules-conditions)
- 서버 커밋이 확인돼야 저장 완료다. 거절/네트워크 중단·응답 불명확은 완료가 아니다. UID/작업 ID를 고정하고 재조회/재시도로 중복 생성과 잘못된 계정 저장을 막는다.
- 초기 계정 캐시는 메모리 중심, 새 저장/수정은 온라인 확인을 기준으로 한다. 영속 오프라인 큐/캐시는 별도 요구·구현/검증 전 활성화하지 않는다. SDK 로컬 상태를 서버 완료로 읽지 않는다.
- 기록 버전/서버 갱신 시각을 검사해 다른 기기의 최신 편집을 오래된 폼이 조용히 덮어쓰지 않게 한다. 충돌은 최신 상태를 확인하고 재적용/취소하게 한다. 필드 합병·트랜잭션/Rules 검사는 구현 브리프에 명시한다. [공식 트랜잭션](https://firebase.google.com/docs/firestore/manage-data/transactions)
- 다른 온라인 기기는 재진입/새로고침/구독 재연결로 최신 상태를 다시 읽는다. 구독만으로 권한 만료·삭제·계정 변경을 처리했다고 가정하지 않는다. 이전 UID/세대의 늦은 응답은 UI에 적용하지 않는다.

## 게스트 기록을 계정에 저장

로그인은 기존 게스트 원본을 자동 전송하지 않는다. ‘이 브라우저 기록을 이 계정에 저장’의 대상/전송 항목을 안내하고 사용자가 선택한다. 취소하면 게스트 원본을 유지하고 계정은 자신의 서버 기록을 조회한다.

작업의 UID·세대·요청 ID를 고정한다. 중복은 기존 서버 기록을 덮어쓰지 않고 게스트에 남겨 안내한다. ‘이동’을 선택해도 서버 성공을 확인한 항목만 로컬 정리하며 부분 실패·서버 성공 후 로컬 정리 실패를 숨기지 않는다. 같은 요청/원본 식별자로 재시도해 중복 생성을 막는다. 전체를 단일 네트워크 트랜잭션처럼 보장하지 않는다. 다른 기기는 서버에 실제 저장된 항목만 조회한다.

기존 Android Room 원본은 자동 업로드/이전하지 않는다. 현재 Android에 새 서버 정책이 구현된 것이 아니며 사용자용 파일 내보내기/가져오기도 복원하지 않는다.

## 삭제·계정 수명

- 사이트 데이터 삭제·캐시 정리·로그아웃은 서버 원본 삭제가 아니다. 정상 계정으로 재로그인하면 서버 원본을 읽는다. 정식 주소가 바뀌어도 같은 운영 프로젝트/UID·허용 origin으로 연결하면 계정 기록을 조회하도록 검증한다. 게스트의 다른 origin 원본까지 자동 이전하지 않는다.
- 개인 기록 삭제·휴지통·복원/영구 삭제는 서버에 반영한다. 기존 휴지통30일은 서버 기준 시각·권한·정리 작업과 맞춘다. 정확히30일 뒤 물리 삭제가 실행됐다고 미리 표시하지 않고 복원 기한·실제 정리/재시도를 검증한다.
- 탈퇴는 최근 재인증, 서버에 지속되는 삭제 요청/접근 정지, 개인 원본·하위 데이터/관련 작업, 인증 계정 정리와 결과 확인을 포함한다. 중간 실패/재시작 뒤 재시도하며 Auth SDK 계정 삭제만으로 전체 삭제 완료라고 표시하지 않는다. 정확한 순서·서버 실행 환경·거절/중단 상태는 WEB-01에서 고정하고 출시 전에 검증한다.
- 탈퇴/정지 후 다른 기기의 기존 토큰·늦은 작업·구독 재연결을 통한 새 서버 접근/쓰기를 막는다. 이미 오프라인에 남은 캐시를 즉시 원격 삭제했다고 약속하지 않는다.
- 서버 개인 원본·인증 정보·공유 사본을 구분한다. 공유 사본은 개인 원본 삭제와 자동 연동하지 않는다. 잔여 참여자/마지막 탈퇴·공유 종료·보존/비식별 세부 정책을 구현 전에 명시한다.
- 운영 백업/사고 복구·보존 기간·삭제 반영은 별도 정책/비용/검사 대상이다. 서버 기록 재조회와 삭제 전 시점 복구·사용자 파일 내보내기를 구분한다. 사용자용 파일 복구 UI는 추가하지 않는다. [하위 데이터 삭제 주의](https://firebase.google.com/docs/firestore/manage-data/delete-data)

WEB-01 탈퇴는 최근5분 재인증 뒤 `deleting`을 커밋하고 Firestore 서버 트리거가 records·sources·Auth·호출 제한을 정리한다. 재시도는 실제 문서 갱신으로 작업을 재발생시킨다. 원본 조회/변경은 pending부터 거절하며 인증 삭제 뒤 기존 토큰도 거절한다. 임의256bit 영수증의 SHA256만 서버 `deletionJobs`에 저장하고 결과 API는 영수증으로 `deleting/deleted/unknown` 상태만 반환한다. UID·이메일·기록은 반환하지 않는다. 클라이언트 sessionStorage에는 해당 탭의 영수증/UID 확인 정보만 남기고 완료 확인 뒤 지운다. 서버 완료 tombstone/영수증은7일, 호출 제한은2일 뒤 TTL 정리 대상이며 정확한 삭제 시각을 보장하지 않는다. 진행 중 작업은 자동 만료시키지 않고 운영자가 실패/재시도를 감시해야 한다.

영수증을 잃은 다른 탭도 아직 유효한 동일 계정을 최근 재인증해 새 영수증으로 삭제 재시도를 요청할 수 있다(최대8개). 서버는 완료 시 최신 영수증 목록을 트랜잭션으로 읽어 모두 처리한다. Auth가 이미 삭제된 뒤 새 영수증을 발급받는 것은 보장하지 않으며 서버 worker 재시도/운영 감시로 정리한다. 이미 완료된 startDeletion 응답은 새 영수증 폴링 없이 완료 처리한다.

## 보안·비용·완료

제공 목적에 맞는 최소 기록을 서버에 보관하고 메모/출처/비밀번호/토큰을 로그·광고·분석 도구에 넣지 않는다. 실제 리전·고지·동의·보존/삭제·문의와 비용을 운영 설정 전에 정한다. 무료1GiB/읽기·쓰기/전송은 개인+공유의 프로젝트 합계이며 계정별 할당량이 아니다. 탈퇴 정리·백업·이미지까지 무료로 확정하지 않는다.

[AC01~AC13](../validation/AUTH-03-account-cloud-policy.md)의 두 독립 브라우저·직접 API 인가·저장 실패·충돌·탈퇴를 실제 구현에서 검증한 뒤 완료를 판단한다. Android/목업의 과거 검사·정책 문서 완료는 이 기능의 통과 증거가 아니다.
