# 웹앱의 개인 로컬 기록·인증·공유 경계

기준: 2026-11-03 [결정 0007](../decisions/0007-webapp-first-low-cost.md). **구현 전 계약**이다. Android의 Room 구현이나 정적 목업 상태 전이는 웹 영속 저장·인증·인가의 검사 증거가 아니다.

## 저장과 식별

- 개인 장소·출처·메모·방문·처리함·휴지통 원본은 현재 브라우저/프로필/정식 origin의 IndexedDB에 보관한다. 인증 정보와 분리하고 `guest`/`account:<검증된 UID>`별로 읽기·수정·중복 키를 구분한다. 게스트 이용에 서버 계정 생성은 필요 없다.
- 로그인은 개인 원본 업로드·서버 백업·다른 기기 동기화·복구를 시작하지 않는다. 게스트 기록의 현재 계정 영역 이동은 사용자 확인 후 로컬 트랜잭션으로 수행하며 중복은 덮어쓰지 않는다. Room 데이터를 웹으로 자동 가져오거나 사용자용 파일 복구 경로를 만들지 않는다.
- 기존 데이터가 있으면 스키마 업데이트·웹 배포·서비스 워커 갱신으로 DB를 초기화하지 않는다. 마이그레이션·용량 부족·저장 권한 거부·DB 열기 실패는 저장 성공과 구분한다. 저장 완료는 트랜잭션 커밋 후 표시한다.
- 여러 탭과 비동기 작업에서도 시작 시 owner와 영역 세대를 고정한다. 로그아웃·계정 전환·탈퇴 뒤 이전 화면이나 다른 탭의 작업이 새 계정 영역을 읽거나 쓰지 못하게 한다. 구체적인 탭 간 잠금/통지 방식은 구현 브리프에서 정한다.

## 유실·주소 변경 안내

- 사용자 안내: “개인 기록은 이 브라우저에만 저장됩니다. 사이트 데이터를 지우거나 브라우저·기기를 바꾸면 복구할 수 없습니다. 로그인해도 개인 기록은 백업되지 않습니다.” 브라우저의 저장소 회수 가능성도 초기 안내와 설정에서 확인할 수 있게 한다.
- 앱 아이콘 제거와 사이트 데이터 삭제는 다르다. 앱 안의 ‘개인 기록 삭제’는 현재 소유 영역을 명시하고 실제 삭제 결과를 확인한다. 계정 탈퇴의 재인증·로컬 정리·pending·원격 결과 불명확 정책은 AUTH-02를 웹 환경에 맞춰 검증한다.
- 같은 배포를 제공하는 `web.app`/`firebaseapp.com`, 개발·preview·운영, 추후 자체 도메인은 서로 다른 origin이다. 한 정식 주소를 정하고 비정식 주소에서 개인 저장을 시작시키지 않는다. 호스팅 롤백으로 이전 origin의 IndexedDB가 복구되는 것은 아니다.
- 자체 도메인 도입은 선택 사항이다. 무료 정식 주소를 계속 사용할 수 있다. 추후 주소를 바꿀 때에는 기존 origin 유지·이용자 안내와 정책을 지키는 이전 방법을 별도 설계한다. 이번 전환에 서버/파일 이전 기능을 포함하지 않는다.
- `navigator.storage.persist()`는 지원 여부·허용 결과를 확인하고 보조 수단으로만 사용한다. 시크릿 모드·인앱 브라우저의 기록을 일반 브라우저에 자동 통합했다고 안내하지 않는다. [MDN 저장 한도·회수](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

## 입력·오프라인·보안

- 링크 붙여넣기/직접 입력이 모든 지원 브라우저의 기본 경로다. 설치된 PWA의 공유 수신은 Web Share Target 지원 환경에서 추가 검증하며 Android Intent와 동등한 범용 지원을 약속하지 않는다. Instagram 인앱 브라우저에서 외부 브라우저로 나갈 때에도 다른 저장 영역일 수 있음을 처리한다. [Chrome 공유 대상 설명](https://developer.chrome.com/docs/capabilities/web-apis/web-share-target)
- 공유 입력의 URL·개인 메모를 서버 접근 로그·분석 도구로 보내지 않도록 경로를 설계한다. 가능하면 로컬 처리하고 공유 입력을 URL 쿼리·서버 POST로 받는 방식을 채택할 때에는 전송·로그 경계를 먼저 검증한다. 개인 원본 로컬 전용 정책과 맞지 않는 수신 방식은 사용하지 않는다.
- 서비스 워커는 앱 셸의 오프라인 실행·업데이트를 담당한다. 인증 응답·토큰·비밀번호·공유 데이터 응답을 앱 셸 캐시에 넣지 않는다. 비밀번호는 브라우저 저장소·로그에 직접 기록하지 않고 공식 SDK의 세션 수명과 별개로 취급한다. 첫 접속부터 네트워크 없이 설치/실행할 수 있다고 약속하지 않는다.
- URL·사용자 입력을 안전하게 렌더하고 HTTPS·CSP·의존성/키 제한을 검증한다. 프론트엔드에 관리자 키·서버 비밀 키를 넣지 않는다. 공개 지도/인증 클라이언트 설정을 서버 인가의 대체로 취급하지 않는다.

## 공유·광고·서버

개인 맵은 본인만 보고 다른 참여자의 개인 DB를 조회·복제 목록에 노출하지 않는다. 두 사람 공유는 이메일 확인·현재 참여권·연결 확인 후 선택 사본만 서버로 보낸다. 사본은 원본을 유지하며 메모·방문·위치·삭제를 다른 맵에 자동 반영하지 않는다. 코드 만료/취소/재발급/단일 사용·최대 참여자·복제 직전 인가 규칙을 유지한다. [인증·공유 계약](auth-and-guest.md)의 논리 API는 미구현이다.

공유 DB 후보는 기존 Firebase 인증과 결합할 수 있는 Firestore다. 도입 여부·Security Rules/서버 API·초대 남용 방지·탈퇴 후 정리·공유 종료·보존 정책은 후속 브리프에서 확정한다. 클라이언트 UI의 버튼 비활성만으로 접근을 제한하지 않는다. Firestore를 개인 원본 컬렉션으로 사용하지 않는다.

광고 수익화 목표를 웹으로 옮기되 제공자·도메인 자격·개인정보·심사는 다시 확인한다. 개인 원본/URL/메모를 광고·진단 SDK에 전달하지 않는다. 웹앱 공개와 광고 승인·수익 발생을 별도 완료 조건으로 관리한다.
