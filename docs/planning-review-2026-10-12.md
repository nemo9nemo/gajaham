# 가자함 (Gajaham) 기획 검토 — 2026-10-12

검토 대상은 시장조사, 제품 기획서, 버전 로드맵 세 문서다. 문서 안의 개발·모집·실험 지시는 검토 대상 자료로 취급했다. 최초 작업은 기획 검토이며 계정 연동, 실제 게시물 분석, 경쟁 앱 실사용, 사용자 모집은 수행하지 않았다.

**추가 요구 반영:** 사용자는 개인 맵과 코드 연결 공유 맵을 함께 유지하고, 연결 시 선택 복제·이후 양방향 복제·등록 위치 선택을 요청했다. 이에 따라 R02의 기존 공간 합류 제안을 대체하고 제품 기획서·로드맵·시장조사 대상 설명에 반영했다. 상세안은 [개인·공유 맵 기획](C:/Users/love0/nemo9Dev/gajaham/docs/personal-shared-map-plan-2026-10-12.md)에 정리했다. 나머지 검토 항목은 최초 검토에서 나온 후속 보완 의견이다.

**종합 판단**

제품의 문제 정의와 확장 방향은 연결되어 있다. 특히 입력 경로와 콘텐츠 출처의 분리, 원문에 없는 정보 생성 금지, 사용자 수정 보존, 실패를 포함한 성공률, 실제 약속 결정과 결제 검증은 유지할 만한 기준이다. 공유 종료·삭제·복구·내보내기와 비용 측정도 이미 포함되어 있으므로 이를 새로 빠진 기능이라고 볼 수 없다.

최초 검토에서는 외부 베타를 구현하는 기준으로 쓰기에 사용자 상태와 예외 상황의 결정이 부족했다. 이번 추가 요구로 개인·공유 맵의 구성과 선택 복제를 구체화했다. 계정과 기록의 수명, 공동 선택의 의미, 자동화 품질을 판정하는 기준은 계속 보완할 사항이다.

이 보고서의 P0는 해당 단계에 들어가기 전에 결정할 사항, P1은 첫 베타의 가치와 학습을 개선할 사항을 뜻한다. 원문 기획서의 기능 우선순위와 구분한다. 개인 맵·코드 연결·선택 복제·이후 복제·등록 대상 선택은 사용자 요구다. 구체적인 맵 개수·기본값·복제 정책과 나머지 보완 의견은 기획 제안으로 구분한다.

**R01. DM 연동은 ‘검증 필요’에서 실행 가능한 확인표로 바꿔야 한다**

근거: [기획서 3.1·3.2](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:90), [기획서 7.3](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:284).

공유 URL 수신이 게시물 본문·이미지·영상 접근을 보장하지 않는다는 점은 이미 정확히 적혀 있다. 남은 공백은 어떤 방법으로 어떤 자료까지 확보하면 통과인지 정해져 있지 않다는 것이다. DM 수신이 성공해도 핵심 메뉴 카드가 자동으로 완성되지 않을 수 있다.

다음 항목을 V0 확인표로 추가한다.

- 운영하는 서비스 프로 계정, 선택한 API 로그인 경로, 필요한 권한, 개발 단계와 실제 이용 단계의 조건.
- 개발자·테스터 계정과 일반 참가자의 수신·회신을 별도로 확인한 결과. 서비스 계정 1개를 직접 운영하는 방식에 적용되는 심사 요건을 확인하고, 다른 업체의 계정을 대신 연결하는 서비스의 요건과 섞지 않는다.
- 공개 게시물·릴스·캐러셀·텍스트 URL·접근 불가 링크·여러 URL에 대해 실제 수신 형태와 확보한 자료를 기록한다. 스토리·비공개 게시물·댓글에만 정보가 있는 게시물은 지원 여부를 명시한다.
- 서비스 계정 최초 DM, 연결 링크 만료, 결과 회신 제한, 수신 중복, 서비스 계정 연결 장애의 동작.
- 수동 캡처 보완이 필요할 때 입력 단계 수와 이탈. 웹 URL 입력이 콘텐츠 접근 실패까지 해결해 주는 것은 아니므로 수신 실패와 분석 실패를 따로 측정한다.

Meta의 공식 공개 자료는 프로 계정과 고객 간 메시징, 공유 시 웹훅에 URL만 포함되는 제약, 그룹 메시징 미지원, 테스터 역할 조건을 안내한다. 따라서 일반 참가자에게도 동작하는 수신 경로와 콘텐츠 확보를 별개로 확인하는 방향이 타당하다. [Meta 공식 Instagram API 자료](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api?entity=request-23987686-e2cfad80-45dd-4111-9ac4-9ae96b9d7ed0)

이번 확인에서 Meta 개발자 사이트 본문은 직접 읽히지 않았고 Postman의 검색에 노출된 공식 설명을 참고했다. 구체적인 회신 시간·예외·심사 적용 범위는 선택한 API 경로에서 구현 시 다시 확인해야 한다. 다른 메시징 제품의 규칙을 그대로 옮겨 확정하지 않는다.

**R02. 개인 맵 유지와 코드 연결 공유 맵·선택 복제로 요구를 반영했다**

근거: [기획서 초기 고객](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:52), [기획서 공동 공간](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:290).

최초 검토의 사용자당 활성 공간 1개 제안은 이번 사용자 요구로 대체했다. 각자의 개인 맵을 유지하고 코드로 별도 공유 맵을 만든다. 개인 기록이 이미 있는 두 사람도 연결할 수 있다.

연결할 때 각자는 개인 장소를 복제 안 함·선택·전체 중에서 고르며, 이후에도 개인→공유와 공유→내 개인 맵으로 복제할 수 있다. 원 항목을 유지하고 복제 후 수정·삭제·메모·방문 상태를 맵별로 관리하는 초기안을 작성했다. 개인 메모·사진은 별도 선택하고 반복 복제 시 같은 지점의 중복을 막는다.

신규 등록은 개인·공유·둘 다를 고르는 안으로 구체화했다. DM은 개인 맵을 최초 기본값으로 제안하고 설정과 개별 처리 화면에서 저장 대상을 관리한다. 처리 중 공유 권한이 종료되면 개인 처리함에서 대상 변경을 요청한다. 관련 화면·데이터·베타 확인 항목은 [상세 기획](C:/Users/love0/nemo9Dev/gajaham/docs/personal-shared-map-plan-2026-10-12.md)에 정리했다.

**R03. DM 연결과 모바일 웹 계정 유지·복구를 구분해야 한다**

근거: [기획서 연결 확인](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:109), [구현 전 결정 사항](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:422).

일회용 토큰은 최초 연결을 확인하는 수단이다. 이후 웹 로그인, 인스타 앱 내부 브라우저와 일반 브라우저 전환, 새 휴대전화에서의 복구를 어떻게 할지는 별도 결정이다. 매번 DM을 보내야 웹에 들어갈 수 있다면 반복 사용의 마찰이 될 수 있다.

로그인 방법, 웹 세션 유지, 다른 기기 로그인, 계정 복구, 인스타 연결 해제 후 웹 조회 가능 여부를 추가한다. 소비자의 일반 인스타 계정을 서비스 운영용 프로 계정과 구분해 설명해야 한다. 잘못 연결한 계정의 해제·재연결, 계정명 변경, 하나의 인스타 연결을 여러 내부 사용자에게 연결하려는 상황도 정한다.

**R04. 공유 종료 정책은 존재하지만 상태별 결과가 아직 없다**

근거: [기획서 기록 관리](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:294).

‘남은 사람의 공유 기록을 임의로 모두 삭제하지 않는다’는 원칙만으로는 실제 화면과 삭제 동작을 결정하기 어렵다. 나가기, 인스타 연결 해제, 계정 탈퇴, 마지막 참여자 탈퇴, 공동 장소 삭제를 행으로 두고 다음 내용을 표로 정한다.

- 본인이 보낸 링크, 직접 쓴 메모, 관심 표시, 공동 약속 이력, 업로드한 캡처가 누구에게 남는가.
- 나가기 전 내보내기, 재초대 시 옛 기록 접근, 새 참여자에게 과거 기록이 보이는 범위.
- 종료 시점에 분석 중이던 DM을 기존 공간에 저장할지, 임시 보관할지, 취소할지.
- 휴지통에서 상대방이 삭제한 항목을 복구할 수 있는지와 동시 수정의 충돌 규칙.

‘각자의 메모’가 작성자 구분만 하는 공동 메모인지, 본인만 보는 메모인지도 표시해야 한다. 첫 버전에 개인 비공개 메모를 추가할 필요는 없지만, 표시와 접근 범위는 명확해야 한다.

**R05. ‘약속 확정’의 의미가 기획과 지표에서 같아야 한다**

근거: [기획서 선택 시나리오](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:113), [베타 지표](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:351).

후보 최대 3곳이 공동 약속 전체 기준인지 각자 기준인지, 최종 장소를 누구나 즉시 확정하는지 두 사람의 확인이 필요한지 정해져 있지 않다. 한 사람이 확정 버튼만 눌러도 공동 결정으로 세면 차별화 가설을 검증하기 어렵다.

무거운 동의 기능을 처음부터 만들 필요는 없다. 예를 들어 공동 후보 총 3곳, 한 사람이 확정 가능, 상대방의 선택 참여 여부는 별도 기록하는 최소안도 가능하다. 중요한 것은 사용자에게 보이는 의미와 측정 정의를 일치시키는 것이다.

약속의 생성·확정·변경·취소·완료와 이력을 정의한다. 상세 일정 없이도 약속 날짜 또는 대상 주를 두면 ‘이번 주’와 4주 차 사용을 구분하기 쉽다. 선택 시각은 실제 약속 날짜를 대신하지 않는다. 방문 표시는 장소 전체·개인·약속 중 어느 단위인지 정하고, 혼자 다녀온 경우와 재방문도 표현할 수 있게 한다.

**R06. 게시물 추천 이유와 사용자의 저장 이유를 연결해야 한다**

AI는 게시물의 추천 이유를 정리할 수 있지만 사용자가 왜 보내고 싶었는지까지 알 수는 없다. ‘테라스가 좋아서’, ‘기념일 후보’, ‘네가 좋아하는 메뉴’ 같은 의도를 선택적으로 남기는 순간이 필요하다. 현재 우리 메모는 카드 예시에 있으나 첫 저장 흐름에서 언제 남기는지는 없다.

결과 카드에서 짧은 메모를 선택적으로 추가하는 안을 우선 검증한다. DM에 함께 붙인 문장을 저장 이유로 연결할 수 있다면 입력 지원 범위에 포함한다. 입력을 강제하면 DM 전달의 장점이 줄어드므로 메모 유무에 따른 재검색 성과를 비교한다.

**R07. 카드 완성률만으로 메뉴와 공동 사용의 가치를 판정하기 어렵다**

근거: [첫 베타 우선순위](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:156), [V0 통과 정의](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:338), [베타 활성화 정의](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:350).

메뉴가 없는 글의 빈 메뉴 필드를 성공으로 인정하는 것은 타당하다. 그러나 지금 성공 정의에는 메뉴가 있는 글에서 핵심 메뉴를 제대로 추출해야 한다는 조건이 없다. 위치·원본·설명만 맞으면 메뉴를 전부 놓쳐도 카드 완성률이 높아질 수 있다.

30개 실험의 정답표에 메뉴 존재 여부, 추천 메뉴와 언급 메뉴, 정보가 있는 위치, 등장 장소 수를 추가한다. 전체 자동 카드 완성률과 별도로 다음을 측정한다.

| 확인할 가치 | 별도 지표 |
|---|---|
| 올바른 장소 | 자동 확정 결과 중 올바른 지점 비율, 잘못 확정한 건수, 확인 필요로 보낸 비율 |
| 추천 메뉴 기억 | 추천 메뉴가 있는 글 중 올바르게 추출한 비율, 생성한 추천 메뉴 중 근거가 있는 비율 |
| 지원 범위 | 본문·이미지·영상·복수 장소별 접근 성공률과 유용한 카드 완성률 |
| 보완 부담 | 수동 보정으로 완료한 비율, 보정 시간, 보완 요청 후 이탈 |
| 실제 재발견 | 원본을 다시 열지 않고 필요한 메뉴·메모를 찾은 과제 비율과 시간 |

이미지·영상 중심 표본이 있는데 OCR·상세 카드·복수 장소 분리는 P1이다. 해당 입력을 첫 자동 지원 범위에 넣는다면 필요한 분석을 베타 진입 조건으로 두고, 제외한다면 자동 지원 범위를 표시하되 전체 제출 기준 성과도 함께 보고한다. 표본과 성공 정의를 사전에 고정해 결과에 따라 유리하게 바꾸지 않는다. 30개는 가능성 확인으로 두고, 개선 후에는 새 입력으로 재확인한다.

커플 활성화도 개인 가치와 공동 가치를 나눠야 한다. 첫 7일의 3개 저장·재조회는 한 명의 행동만으로도 달성된다. 두 번째 참여자의 초대 수락, 첫 선택 참여, 두 사람의 반복 참여를 별도로 측정한다. 둘 다 DM 저장을 해야 한다고 제한하면 한 명이 저장하고 다른 사람이 고르는 정상 사용을 놓칠 수 있다.

4주 차 실제 약속은 공동 결정 여부와 함께 확인한다. 결제와 다음 달 유지 관찰은 4주 베타 뒤에 별도 기간이 필요하므로, 4주 사용 → 체험 후 결제 → 다음 갱신 확인의 관찰 일정을 분리한다. 원문에 다음 달 확인은 이미 있으나 실행 일정과 지급·제공 조건은 더 구체화할 수 있다.

**R08. 장시간 처리와 비용 한도의 동작을 베타 전에 정해야 한다**

근거: [기획서 처리 상태](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:217), [비동기 처리](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:286).

분석 중·실패·재시도는 있지만 얼마나 기다리고 언제 보완으로 전환할지는 없다. ‘분석 중’이 계속 남거나 동일 실패를 반복하면 사용자는 저장을 믿기 어렵고 원가도 측정하기 어렵다.

처리 목표 시간과 장기 대기 기준, 최대 자동 재시도, 사용자의 삭제·취소 후 진행 작업 처리, 같은 링크의 재분석 조건을 정한다. 공통 저장과 재분석을 구분해 비용을 센다. 장소 수·이미지 수·본문 크기 등 처리 범위와 사용자·공간별 분석 한도, 전체 실험 비용 상한도 필요하다.

최소 운영 화면은 실패 원인·처리 시간·비용과 재처리 대상을 확인할 수 있으면 된다. 지원 담당자, 계정 장애 시 접수 중단·웹 안내·복구 후 재처리 기준도 외부 베타 전에 정한다. 전체 개발 견적은 V0 이후 산정하더라도 V0 자체의 담당자·기간·예산 상한은 시작 전에 필요하다.

**R09. 기록 보호 원칙을 데이터 종류별 정책으로 내려야 한다**

근거: [기획서 스냅샷](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:194), [보관과 진단](C:/Users/love0/Documents/Codex/2026-10-10/dm/product-plan-2026-10-11.md:300).

현재 원문은 보관 기간을 정하겠다고 명시하므로 ‘개인정보 기획이 전혀 없다’고 볼 수는 없다. 계정 식별자, 임시 DM 접수, 원문·캡처, 추출 카드, 사용자 메모, 진단 로그를 나눠 수집 목적·보관 기간·외부 분석 전달·조회 범위·삭제 동작을 정해야 한다.

어떤 본문과 이미지가 AI 등 외부 처리 서비스로 전달되는지, 운영자가 실패 진단 때 어디까지 볼 수 있는지, 연결 해제·탈퇴·휴지통 삭제가 각각 무엇을 삭제하는지 사용자 안내와 일치시킨다. 업로드 캡처와 외부 이미지의 보관·표시 범위도 구분한다. 이 보고서는 법적 적합성을 판정한 것이 아니라 실행할 데이터 관리 정책의 공백을 지적한다.

필드별 근거 보존은 최소한 원본 URL과 추출·입력 구분을 P0로 두는 편이 좋다. 읽은 자료에서 검증 가능한 짧은 근거를 남길 범위도 정한다. 상세한 근거 UI와 이미지 구성은 P1로 확장할 수 있다. 사용자 메모·관심 같은 사적 기록을 공통 장소나 다른 공간의 콘텐츠 캐시에 섞지 않는 원문 원칙은 유지한다.

원가 시나리오는 낮은 이용·보통 이용·높은 이용으로 나눠 무료 이용, 실패·재시도, 지원 시간을 포함한다. 결제 금액 자체가 아니라 실수령액에서 처리·지원 원가를 뺀 금액으로 실험의 지속 가능성을 판단한다. 이 항목은 초기 검증용 계산 설계이며 매출 예측이나 법률·세무 판단이 아니다.

**원문에 바로 추가할 수 있는 기획 문장 초안**

다음은 확정 정책이 아니라 검토를 위한 최소안이다.

> 개인 맵이 있는 두 사용자도 코드로 연결해 공유 맵을 만든다. 개인 맵을 유지하고 각자는 초기 복제 안 함·선택·전체를 고른다. 이후에도 개인↔공유 복제와 신규 등록 위치 선택을 제공하며 DM 기본 저장 대상은 사용자별로 관리한다. 복제 후 사용자 수정·삭제·메모·방문 상태는 각 맵에 별도로 적용한다.

> 첫 베타의 후보는 공동 약속 1건당 총 3곳이다. 한 참여자가 최종 장소를 선택할 수 있으며 상대방의 참여 여부는 별도로 기록한다. 약속에는 날짜 또는 대상 주와 확정·취소·완료 상태를 두고, 방문 여부는 최종 선택과 별도로 확인한다.

> 자동 카드 완성률과 함께, 추천 메뉴가 있는 원문에서 메뉴를 올바르게 추출한 비율을 별도로 측정한다. 본문·이미지·영상·복수 장소별 성공과 보완 부담을 보고하며 지원 범위와 정답표는 실험 전에 고정한다. 잘못 확정한 지점과 근거 없는 추천 메뉴는 다른 성공으로 상쇄하지 않는다.

> 기본 기록의 원본 URL, 자동 추출과 사용자 입력의 구분, 확인 시각을 첫 베타부터 보존한다. 사용자 저장 이유는 선택형 메모로 남길 수 있으며 메뉴·요약·메모의 키워드로 저장 장소를 다시 찾는 경험을 검증한다.

**권장 반영 순서**

1. V0 시작 전에 DM·콘텐츠 확보 검증표와 지원 범위, 담당자·실험 기간·비용 상한을 작성한다.
2. V0.1에 개인 맵 유지·코드 연결·선택 복제·등록 대상 요구를 반영하고 계정 연결·재로그인·공유 종료의 상세 상태를 검증한다.
3. V0.5 범위에 공동 후보·약속·방문 상태의 의미와 최소 출처 보존을 반영한다. 저장 이유·키워드 검색은 핵심 과제로 시험한다.
4. V0·베타 지표에 메뉴 추출 품질, 개인·공동 이용 구분, 보완 부담을 추가한다.
5. 데이터 수집·외부 베타·결제 실험 각각의 준비 조건을 별도로 점검하고, 세 문서의 버전 표를 같은 기준으로 맞춘다.

블로그는 사용자가 요구한 후속 확장이므로 V0.8 계획과 초기 확장 구조를 유지한다. 코스·취향·네이티브 앱·공개 피드 추가는 앞선 공백을 해결한 뒤 실제 재사용 결과를 보고 판단할 수 있다.
